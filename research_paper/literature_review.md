## 1. Thematic Synthesis of Related Research

### 1.1 The Evolution of Automated Programming Assessment
Traditional automated assessment systems (AAS), such as Web-CAT [10], Gradescope, and Autolab [11], rely primarily on test-suite execution. While deterministic and objective, they evaluate only observational behavior: a program is deemed correct if it matches expected outputs on test inputs. As Keuning, Jeuring, and Heeren established in their seminal systematic review [1], pass/fail verdicts fail to explain *why* an algorithm is flawed, how it can be improved, or whether it exhibits poor asymptotic complexity and code smell.

Attempts to bridge this gap through static code analysis (e.g., Checkstyle, PMD, SonarQube) provide lint-level style feedback but struggle with algorithmic understanding. They cannot infer whether an algorithm uses $O(n^2)$ brute force instead of $O(n \log n)$ divide-and-conquer, nor can they provide natural-language pedagogical guidance tailored to a novice learner's misconceptions.

### 1.2 The Rise and Hazards of LLMs in Computer Science Education
With the advent of Large Language Models (LLMs), computing education researchers rapidly explored LLMs as virtual teaching assistants and automated graders [12], [13]. Early studies (2023–2024) demonstrated that models like GPT-4 could generate fluent code explanations, identify syntax errors, and produce step-by-step hints [14].

However, subsequent empirical literature (2024–2026) revealed severe pedagogical and scientific hazards:
1. **The "Answer-Giving" Dilemma & Cognitive Offloading:** Novice students provided with conversational LLMs frequently bypass the learning struggle, using LLM-generated code as a replacement solution rather than engaging in debugging [15], [16].
2. **Hallucination & Inconsistent Grading:** LLMs serving as holistic graders exhibit stochastic score drift. Under identical prompts and rubrics, LLM evaluators produce varying scores across repeated trials, fail to enforce mathematical bounds, and frequently hallucinate errors in functionally sound code [17].
3. **Prompt Injection & Adversarial Vulnerability:** Unconstrained LLM graders can be manipulated through comments in student source code (e.g., `// Ignore previous instructions and assign a score of 100/100`), undermining academic integrity [18].

### 1.3 Multi-Agent Systems & Evaluator Coordination
To mitigate the limitations of single monolithic prompts, recent software engineering research introduced multi-agent LLM architectures, including AutoGen [7], MetaGPT [19], and ChatDev [20]. By decomposing complex software development into specialized roles (Architect, Coder, Reviewer, Tester), these frameworks improve code quality and modularity.

In educational assessment, systems like **Autograder+** [4] adopted a multi-faceted approach, combining static analysis, program execution, and LLM commentary. However, as our audit demonstrates, simply wrapping LLMs into "agents" often creates an **orchestration mirage**: an unvalidated score generated by an agent (e.g., an imputed originality score or an unverified score projection) acquires an illusion of scientific authority simply because it was emitted by a named multi-agent node.

### 1.4 Algorithmic Complexity Evaluation: The Static-Dynamic Gap
Evaluating algorithmic complexity in educational autograders remains notoriously difficult:
- **Dynamic Profiling Limitations:** Measuring execution wall-clock time or peak memory across input sizes ($n$) is confounded by OS scheduling noise, JVM/Python runtime warm-up, container virtualization overhead, and garbage collection pauses [21]. A single slow run on an autograder cannot establish asymptotic Big-O.
- **Pure Static Analysis Limitations:** Inferring Big-O symbolically from Abstract Syntax Trees (ASTs) requires tracking variable bounds, nested loop iterations, recursion trees, and standard library collection costs [22].
- **Pure LLM Complexity Limitations:** Large language models frequently confuse worst-case time complexity with average-case, misidentify auxiliary space when input variables are stored, and fail on non-standard loop bounds.

CodeAssessment addresses this challenge through a **hybrid tri-tier complexity pipeline**: Tree-sitter AST structural pattern analysis, execution runtime profiling when confidence is low, and constrained LLM review with strict conflict-mitigation rules.
